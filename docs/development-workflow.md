# AI Music 开发工作流讨论记录

2026-09-27 与用户讨论形成的四步框架；开发执行要点已写入 [ai-music-developer skill](../.agents/skills/ai-music-developer/SKILL.md)，不改变 [AGENTS.md](../AGENTS.md) 中“用户验收后由用户亲自启动独立 review”的规则。AI Music 默认在当前工程的 `main` 上开发；用户明确要求时可以切换或创建分支。始终不创建 worktree；如确需另一个工程，由用户明确提出。

1. **需求卡片**：在对应功能文档中记录当前行为、失败行为和少量验收场景；用户后续修正直接更新最终要求，不让早期方案覆盖新决定。
2. **开发与自测**：开发复现问题，修复时加入有意义的回归测试。小调整仍须测试：至少跑相关测试与静态/差异检查；涉及实际界面、设备或网络行为时做匹配的手动验证。准备体验包时再跑完整测试并核实安装结果，避免每一处文字或图标微调都机械重装手机。并发/批量逻辑重点检查取消、乱序完成、重试、去重、源失败和持久化。
3. **交用户体验**：开发清楚说明改了什么、自己实际测了什么、什么仍需用户试。开发自测不能写成用户验收。记录安装包版本与哈希以及对应代码阶段；同一工程和分支也可能因构建时间不同而使手机包落后于 review 修复。
4. **用户验收与独立 review**：只有用户确认体验并亲自在 review 会话发起后，reviewer 才审查；开发修复具体问题并验证，reviewer 复核结论。若 review 后代码又变，应明确当前手机包是否包含修复；修复影响可见体验时，重新交用户试用，不能由开发或 reviewer 代为验收。提交、推送按用户已有授权执行。

每天一份 [工作日志](worklog/README.md)，分开写开发/自测和独立 review，并明确用户实际体验反馈。`CURRENT_STATE.md` 只保留当前基线与日志入口；无需在每条记录重复暂存、提交、推送状态。
