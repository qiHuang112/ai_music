# AI Music 开发工作流讨论记录

2026-10-10最新决定：开发、手机自测、代码／发布审查和交付全部集中在 [ai-music-developer skill](../.agents/skills/ai-music-developer/SKILL.md)。固定 **AI music-代码 review** 会话已归档，旧固定会话交接规则不再使用。AI Music 默认在当前工程的 `main` 上开发；用户明确要求时可以切换或创建分支，始终不创建 worktree。

1. **需求卡片**：在对应功能文档中记录当前行为、失败行为和少量验收场景；用户后续修正直接更新最终要求，不让早期方案覆盖新决定。
2. **开发与自测**：复现问题，修复时加入有意义的回归测试，检查取消、乱序、重试、去重、源失败和持久化。完成一轮修复后跑完整适用测试、分析和差异检查，校验归档debug，直接保留数据安装77，再实机复测原问题和相关交互；用户已持续授权，无需重复要求安装。不能以宿主机接口探针或安装成功代替实机自测。
3. **交用户体验**：开发清楚说明修改、实际测试和手机版本／哈希／代码阶段，自测通过后才交用户验收。开发自测不能写成用户验收，不能让用户代替开发复现未验证的修复。
4. **“走流程”独立审查**：用户触发后，开发启动一个全新临时只读审查子agent，按同一skill中的代码／发布审查指引检查固定的全部待交付差异和实机证据；不再唤醒固定review会话或创建永久角色。发现问题由开发修复、测试和实机复测，再交回复核；通过前不发布。仅要求review时到审查结束，不自动发布。
5. **自动交付**：“走流程”已授权审查通过后的提交推送和发布。开发提交已审查文件，经统一脚本触发GitHub CI，跟进同一提交的签名构建／正式Release；再确认Mac镜像了相同APK，核对局域网元数据并完整下载验证大小／哈希，全程保留历史包。审查、CI或局域网失败则继续排查并准确报告，不把交接或push成功作为流程完成。发布细节见[Android更新](android-updates.md)。

每天一份 [工作日志](worklog/README.md)，分开写开发/自测和独立 review，并明确用户实际体验反馈。`CURRENT_STATE.md` 只保留当前基线与日志入口；无需在每条记录重复暂存、提交、推送状态。
