# 下载与本地音乐按日期分组

## 2026-10-11 下载管理重新布局

用户痛点：搜索框埋在歌单与任务之后，需要滑动很久；长列表难以快速找到歌曲、歌单或失败任务。新页面使用固定顶部搜索与「已下载／任务／歌单」直接切换，默认进入已下载。关键词按歌曲、歌手／任务信息／歌单名称筛选对应区域，切区保留关键词；搜索和切区均不需要先回列表顶部。

- 已下载：保留播放、单曲删除、下载时间／首字母排序、日期分组折叠吸顶、单日／日期范围／未知日期筛选。固定工具行显示当前数量、筛选和排序；搜索命中的旧日期自动展开。
- 任务：保留活动进度、取消、历史状态／错误原因、清除记录和日期分组；提供全部／进行中／失败／已完成／已取消的直接状态筛选，活动任务不受历史日期条件限制。
- 歌单：名称搜索，保留总曲目／已下载数量、打开详情、整单下载及批次进度；不混进缓存歌曲列表。
- 刷新与局域网同步入口始终在顶部。局域网同步展开独立面板，保留服务地址、扫描同步、进度、结果摘要及错误；不再排在长列表末尾。切区保留各自滚动位置，重新搜索／筛选回到结果顶部，长列表惰性构建。
- 验证：27张以上歌单和长历史不阻挡搜索；滚到深处仍能搜索／切区；歌曲、任务、歌单关键词定位和清空；失败筛选与活动取消／历史清除；日期与搜索叠加、排序后播放索引；窄屏大字体／键盘下布局；局域网面板取消与原进度；77实机完整队列和新下载管理一起验证，不为测试删除用户歌曲或启动整单下载。

- 下载管理“最近任务”按本地终结时间分组，新日期在前；显示今天、昨天、前天、3～6天前，更早显示月日，跨年带年份，缺时间显示“日期未知”。每组分别统计下载成功、复用缓存、失败、取消，避免冒充下载成功数。
- 新任务记录创建/完成时间，最近任务终结状态独立持久化，重启可读；保持原同歌曲仅保留最近一次任务的语义。清除任务后不因异步历史读取复活；只在终结/清除时写历史，字节进度不写盘、不额外刷新首页。旧版本未记录任务历史，不补造；已有缓存按原cachedAt分组。
- “我的缓存列表→本地”及下载管理“已缓存音乐”，默认下载时间排序时按同样日期分组、显示当前组歌曲数；切首字母排序保留原平铺逻辑。搜索后数量是筛选结果；日期标题不参与播放队列、多选或删除。自建歌单原曲目顺序保持。

## 用户追加：折叠、吸顶与日期筛选

- 点击日期标题收起/展开本组，箭头及无障碍展开状态同步；各组独立保存本页折叠状态。最近任务和缓存歌曲分别管理折叠状态。
- 日期标题在对应组滚动时吸顶，下一日期推走上一日期；离开该区域不遮挡其他区域。长列表使用惰性sliver列表。
- 本地页及下载管理右上角提供日期筛选，菜单列出实际有记录的日期（含未知日期）及“全部日期”。下载管理同时筛选最近任务和已缓存音乐，正在下载及歌单下载操作继续可见。日期条件与文字搜索叠加，首字母排序也遵守日期筛选；日期筛选不删除或修改数据。
- 验证：点击今天可收起再次展开；长组滚动吸顶、跨组推走；按昨天筛选只显示昨天歌曲，返回全部日期恢复；文字搜索叠加筛选无结果；日期标题不进入播放队列与多选。

## 多年历史与滑动性能（本轮取代逐天展开和日期枚举菜单）

- 近7天按天直接显示；更早的本年记录按月默认收起，往年按年默认收起，展开年看月、展开月看日。只聚合较旧部分，跨月/跨年的近7天不会重复进入年月汇总；未知日期单独一组，汇总数量不重复。
- 日期菜单固定为全部日期、选择一天（日历）、选择日期范围（日历起止日），有未知日期时才增加该项。日期范围包含首尾日期；取消日历保持原筛选。筛选/搜索命中的旧记录自动展开便于查看。
- 滑动排查：8125在77的同一178首本地列表进行8次滑动采样，461帧中UI build的p95为23.965ms、峰值43.25ms，raster p95为6.002ms、峰值9.617ms。问题主要在UI线程，debug采样不等同release性能。旧实现每一天一个SliverList，Flutter会布局屏幕外各delegate首行，日期多时工作量随天数增长；折叠年月后不创建其子列表。歌曲行各自订阅播放流也会在滚入时重复订阅和构建，改为列表共享一次订阅。
- 本轮验证：365天/跨年分层覆盖与去重、旧年月默认不构建歌曲、年→月→日展开及吸顶、单日/范围日历取消和首尾边界、搜索组合、播放/多选；同设备同滑动动作复测并如实记录局限。

### 本轮实测结论

同一77手机、178首本地歌曲，8次500ms上下滑动，采集Flutter.Frame事件（单次对照，不作为通用性能承诺）：

| 构建 | 帧数 | UI build p95 | raster p95 | elapsed p95 | elapsed最大值 |
|---|---:|---:|---:|---:|---:|
| 8125 debug | 461 | 23.965ms | 6.002ms | 30.342ms | 46.920ms |
| 8126 debug | 432 | 25.245ms | 5.894ms | 31.062ms | 49.237ms |
| 8126 profile | 377 | 2.710ms | 2.622ms | 5.606ms | 6.997ms |

- debug新旧对照的中位UI耗时从3.921ms变为3.513ms，elapsed超过16.7ms的样本比例从81/461变为57/432，但p95没有显著改善，不能声称debug慢帧已消除。
- 8126 debug另一次CPU采样中，2848个样本有650个包含mount/inflateWidget/firstBuild，慢帧主要涉及新行创建。相同新代码在profile模式下整帧最大6.997ms，说明此设备、此场景中剩余debug运行开销影响明显；未测试191 release，不推断其帧率。
- profile仅临时排查，签名相同、保留数据；完成后已恢复77 debug8126。多年收拢减少不可见子列表、共享播放监听已通过独立结构回归；178首实机只有今天/昨天，不能据此声称已测实机多年数据。
