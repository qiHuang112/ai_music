2026-10-08 用户要求：Auto 模式下，某个来源频繁失败后，本次应用运行不再持续请求该来源，后续使用另一个来源。设置中的明确单选来源仍尊重用户选择。

## 行为

- 应用共用的 `RemoteMusicResolver` 保存运行期间的来源健康状态，不写入偏好或磁盘。重新打开应用后重新尝试两源。
- 每个来源的搜索、解析、音频传输分别统计连续失败；任一阶段连续 3 次业务操作出现连接、超时、服务端、限流或响应协议故障后，暂停 Auto 对该来源的新请求。搜索内部的 HTTP 重试、分页和多关键词仍只算一次业务操作。
- 成功请求（包括正常的空结果）重置尚未降级来源在该阶段的连续失败次数。搜索成功不能掩盖解析／音频传输的持续故障。单曲无地址、无品质、加密格式、不存在的歌曲、过期候选及用户取消不视为整个来源故障。
- 降级后，先前并行请求晚到的成功结果、用户手动测试成功均不会自动恢复 Auto 的请求。来源健康状态可以告知界面当前可用源及降级原因。
- Auto 的常规搜索、渐进搜索、截图／歌单快捷查询与解析音频共用状态。候选分数相同时 FLAC 优先；不同分数仍按匹配分数排序。
- 每个来源最多同时执行 2 个 Auto 业务操作。排队操作在开始前重新检查降级状态，已降级时直接转由调用者选择其他来源；已经发出的网络请求允许结束，不再发起新请求。
- 渐进搜索取消后，不再发出该搜索尚在排队的请求，已发出请求的晚到结果不更新健康状态。
- 两源都降级时立即返回可读错误，提示手动选源重试或重新打开应用，不循环请求失败来源。

## 调用约定

`AutoSourceHealthResolver` 是可选能力，不改变 `MusicResolver` 等原有接口。调用方在 Auto 播放／下载中使用 `resolveForSourceMode(candidate, mode, quality: ...)`，并在旧候选来源已降级时重新匹配可用源。原 `resolve`／`resolveAtQuality` 保留手选／兼容语义，不阻止明确选择的来源。

解析阶段失败由 resolver 自己记录；播放或下载阶段新增的音频网络错误可用 `reportSourceFailure` 上报，不能对同一次解析失败再计一次。`reportSourceSuccess` 用于确认音频传输成功。单纯访问本地缓存不触发网络健康计数。

## 回归与试用

自动化覆盖共享计数、内部重试只记一次、空结果、单曲错误、成功重置、迟到成功、手选绕过、两源不可用、并发上限、排队失效与取消。具体运行结果由主开发统一执行测试后记录。

实机试用场景：Auto 连续遇到同一来源故障后继续搜歌／播放／导入歌单，应只请求另一来源；用户在设置手动选回该来源时仍可重试；彻底结束应用后重新打开，应恢复可尝试状态；正常无搜索结果不应触发降级。

## 2026-10-09 独立审查补充

Auto媒体失败恢复捕获App和系统播控命令revision；元数据修复、备用源搜索／解析、等待加载锁及原生加载返回后均核对恢复是否仍有效。用户暂停、切歌或停止后，旧恢复不能重新发起播放，旧恢复错误也不能覆盖新操作。系统暂停、下一首／上一首、队列点选及停止在原生异步动作前记录意图。

匹配器内部自动查询缓存和并发请求按当前可用源集合隔离，缓存与请求返回均过滤停用来源；Auto请求途中健康集合改变时，按新集合重新查询，再推荐可用候选。截图多阶段合并最终排名也再次过滤。手动明确指定来源不受Auto健康过滤影响。
